Reserva + pago + aviso al dueño

Primero se verifica el pago. Después se avisa.

Así funcionaría una reserva con pago para barbería, estética, pilates o gimnasio. El sitio estático no puede acreditar un pago: la confirmación depende de un servidor que recibe el aviso firmado del proveedor y consulta el pago antes de confirmar.

Pago deshabilitado: esta página está abierta como archivo estático. Para probar el flujo completo ejecutá python integration/sandbox_server.py y abrí http://127.0.0.1:8767/integration/. El sandbox usa un proveedor SIMULADO local; no es Mercado Pago y no envía emails.

El recorrido seguro

  1. Elegís turno. El navegador envía sólo el turno y un contacto. Nunca el importe.
  2. El servidor reserva por unos minutos y crea el pago en el proveedor con el precio de su propio catálogo.
  3. Pagás fuera del sitio, en el checkout del proveedor. El sitio no ve ni guarda tarjetas.
  4. El proveedor avisa al servidor con un webhook firmado. El servidor valida la firma y consulta el pago.
  5. Recién con el pago aprobado se confirma el turno y se envía el email al dueño.

Volver del checkout con ?status=approved en la URL no confirma nada: esta página siempre le pregunta el estado al servidor.

Probar el flujo

El sandbox rechaza emails reales. No cargues datos personales.

Lo que falta y no se puede simular

  • Cuenta de Mercado Pago del comercio, aplicación, credenciales de prueba y luego de producción, cargadas sólo en el servidor.
  • Backend desplegado con HTTPS, base de datos, tareas en segundo plano y conciliación periódica.
  • Proveedor de email con dominio propio verificado (por ejemplo Resend) y remitente autorizado.
  • Política de cancelación, reembolso y no-show escrita y aprobada por el negocio.
  • Prueba con cuenta compradora de test y simulador de webhooks del panel antes de cobrar de verdad.
